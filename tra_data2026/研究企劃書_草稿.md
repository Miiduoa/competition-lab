## 壹、研究摘要

本企劃對應競賽議題二「旅途探索家」（旅運觀光），並銜接五大明珠中「運輸本業」與「臺鐵假期」主軸，提出 **RailFlow-DSS（鐵道旅運負荷預測決策支援系統）**：以國營臺灣鐵路股份有限公司公開之「每日各站點進出站人數」為核心資料，輔以車站基本資料、定期／每日時刻表、營運通阻與節日／活動日曆等開放資料，建構「車站日層級旅運負荷預測 → 可解釋歸因 → 營運／旅客端決策建議」之完整決策支援閉環。

研究動機源於實務常見落差：車站與車廂尖峰負荷、連假疏運與觀光節點人潮，往往仰賴經驗法則與事後統計，難以在事前同時回答三個管理問題——**未來會有多少人？依據是什麼？此刻該如何行動？** 本企劃不以單一預測分數為唯一目標，而將機器學習嵌入資訊系統與管理流程，強調資料品質、基準模型對照、時間切分評估，以及可被調度／場站人員理解的解釋與建議語言。

方法上，先建立可重現之資料管線（清洗、站碼對照、日曆特徵、滯後與滾動統計、通阻／連假事件標記），再以移動平均／季節均值為 baseline，並以樹系或梯度提升等可解釋模型輸出未來 7–14 日各站進出站量預測；同步產出特徵重要性、類似歷史日檢索與規則型建議（人力／疏導／旅客改乘提示之原型邏輯）。系統以互動儀表板呈現 KPI、預測曲線、解釋區與建議區，支援依路線、車站等級與節日情境篩選。

預期貢獻包括：（1）示範以臺鐵開放資料驅動、可落地之旅運負荷決策支援原型；（2）提出可複製的評估框架（預測誤差＋決策效用假設任務）；（3）為後續銜接內部機敏資料（通過初選後）預留擴充介面。本企劃於海選階段以公開資料完成完整研究設計與原型規劃，決選階段可深化 Demo 與案例驗證。

**關鍵字**：旅運負荷預測、決策支援系統、可解釋儀表板、進出站人數、開放資料、臺鐵

## 貳、研究動機與目的

### 一、研究動機

（一）公共運輸數據價值需轉譯為「可執行決策」  
開放資料已具備車站運量、時刻與通阻等基礎，但若僅停留於報表或單次分析，難以支援日常調度、連假整備與觀光疏運。數據應用應延伸至「事前預測—事中因應—事後檢討」之管理循環。

（二）旅運尖峰具高度時空異質性  
都會轉運站、觀光支線站、節慶臨時湧入站之負荷模式不同；同一車站在平日尖峰、周末、連假前一日之形態亦異。需要分站、分情境之模型與可視化，而非全線單一平均。

（三）「黑箱預測」難以進入營運現場  
場站與運務人員需要知道「為何今天預估偏高／偏低」：是否因連假、是否類似某歷史連假、是否與通阻後效應有關。可解釋性與相似案例檢索，是決策支援被採納的關鍵。

（四）對齊競賽「旅途探索家」與運輸本業升級  
議題二強調旅遊需求與人流預測、即時旅運資訊與導引；本企劃以進出站人流預測為核心，向上可延伸觀光疏運與行程建議，向下可支援站內疏導與運能整備，形成旅客體驗與營運效率雙贏之構想。

### 二、研究目的

1. **建構**以臺鐵開放資料為基礎之車站日層級進出站人數預測模型，並建立可重現之資料與實驗管線。  
2. **設計**可解釋決策支援儀表板，整合 KPI、預測、特徵／案例解釋與文字化營運建議。  
3. **提出**預測誤差指標與決策效用假設任務之雙軌評估，證明相對 baseline 之增益。  
4. **規劃**與「臺鐵假期／運輸本業」相關之應用情境（連假疏運、觀光站尖峰預警、旅客資訊提示原型）。  
5. **確保**資料來源合法公開、方法可審計，並預留晉級後銜接內部資料之介面。

### 三、研究問題

RQ1：以公開進出站日資料，能否在時間切分下穩定優於簡易基準模型？  
RQ2：哪些特徵（日曆、滯後、滾動、事件）對不同類型車站最具解釋力？  
RQ3：將預測結果轉譯為建議語言後，是否提升「假設調度任務」之決策一致性與反應時間（原型評估）？

## 參、適用範圍

### 一、空間範圍

以臺鐵全線有進出站統計之車站為對象；原型優先聚焦：  
1. 高運量轉運／都會站（負荷管理、疏導）  
2. 觀光支線或假期熱點站（旅遊人流預測）  
3. 對照組：中低運量站（驗證模型在稀疏序列上之穩定性）

### 二、時間範圍

海選企劃階段：規劃使用 2019 年以降公開日資料（含疫情前後結構變化討論）；實際建模視下載完整度採近 2–3 年為主訓練窗，並保留更長歷史作季節對照。預測視野建議 7 日（營運整備）與 14 日（連假整備）。

### 三、應用範圍（In Scope）

- 車站日進出站量預測與異常偏離警示  
- 可解釋儀表板與規則型建議原型  
- 公開資料整合方法與資料來源表完整揭露  

### 四、非適用範圍（Out of Scope／海選階段）

- 不等同於正式 ATS／票務系統即時調度指令  
- 不使用未授權之內部機敏票證個資或未公開 OD 明細  
- 不以影像監視或 AIoT 硬體部署為本期交付（可列為延伸）  
- 不宣稱可取代專業運務判斷；系統定位為**輔助決策**

## 肆、名詞解釋

1. **進出站人數**：旅客通過車站閘門進站／出站之計次統計（日彙總）。  
2. **旅運負荷**：本研究操作化為車站日進站量、出站量及其合計與相對歷史常態之偏離程度。  
3. **決策支援系統（DSS）**：整合資料、模型與人機介面，協助決策者改善決策品質與速度之資訊系統。  
4. **Baseline（基準模型）**：如七日移動平均、同星期季節均值等簡單可解釋方法，作為進階模型增益對照。  
5. **時間切分驗證**：依時間先後劃分訓練／驗證／測試，避免未來資訊洩漏。  
6. **可解釋性**：使模型輸出可被人類理解之機制，含特徵重要性、部分依賴、相似歷史日等。  
7. **通阻**：營運異常／路線中斷等事件，可能造成當日與後續數日運量結構改變。  
8. **五大明珠**：運輸本業、資產開發、臺鐵便當、臺鐵夢工場、臺鐵假期等發展主軸。  
9. **RailFlow-DSS**：本企劃提出之鐵道旅運負荷預測決策支援系統原型名稱。

### 二、文獻與實務脈絡（精要）

公共運輸需求預測常見方法包含時間序列分解、機器學習與深度學習；實務導入瓶頸多在資料介接、指標定義不一致與「模型結果無法被調度語言吸收」。決策支援文獻強調：預測只是手段，改善決策才是目的。本企劃採「輕量可解釋模型＋強流程紀律＋儀表板轉譯」路線，優先保證可審計與可 Demo，再視需要加深模型複雜度。

與「旅途探索家」之連結：人流預測是觀光接駁、動態導引與疏運整備的上游能力；與「運輸本業」之連結：場站人力與旅客動線管理直接影響服務穩定與安全體感（與智慧守護者之人流風險管理可在延伸議題銜接，但本期主軸仍為旅運預測 DSS）。

### 四、研究方法與分析流程

```
圖 2　資料管線與特徵工程流程（示意）

原始 JSON／API
   → Schema 檢核、站碼對照、日曆對齊
   → 衍生：進+出、星期、月份、連假距離、班次數代理
   → 滯後特徵 lag_1/7/14/28；滾動 mean/std
   → 通阻事件窗（當日、+1～+3 日）
   → 訓練／驗證／測試（時間切分）
   → Baseline vs 進階模型
   → 解釋產物 + 建議規則
   → 儀表板
```

#### （一）探索性分析（EDA）

1. 全線與分群車站之週季節、年季節、連假效應。  
2. 進站／出站不對稱（通學、觀光目的地站）。  
3. 通阻日與後續恢復曲線。  
4. 觀光線與縱貫幹線負荷相關性（疏運聯動初步觀察）。

#### （二）特徵工程

**表 3　特徵清單（摘要）**

| 類別 | 特徵例 | 說明 |
|------|--------|------|
| 日曆 | dow、month、is_holiday、days_to_holiday | 捕捉週期與連假 |
| 滯後 | lag_1, lag_7, lag_14, lag_28 | 短期與週週期記憶 |
| 滾動 | roll7_mean, roll7_std, roll28_mean | 水準與波動 |
| 營運 | daily_train_stops_proxy | 由時刻表聚合之停靠／班次代理 |
| 事件 | alert_flag, alert_lag1_3 | 通阻當日與延遲效應 |
| 站點 | station_tier, is_tourist_line | 來自車站屬性分群 |

#### （三）模型策略

1. **Baseline**：七日移動平均；「去年同星期／同節日」對照（若資料長度足夠）。  
2. **進階模型（海選規劃／決選實作）**：Random Forest 或 Gradient Boosting（輕量、可出特徵重要性）；必要時加簡單時序模型作對照。  
3. **分群建模**：高運量站獨立模型 vs 中低運量站 pooled 模型，平衡資料稀疏與專精度。  
4. **多目標**：分別預測進站、出站，再合成總負荷；或直接預測總量並分解（比較後擇優）。

#### （四）異常與預警規則（決策層）

定義「相對常態偏離」：例如預測值或實測值超過同車站同星期歷史 P90，或超過 roll28_mean + k×roll28_std。預警分級：留意／整備／強化疏導（文案模板，供人工覆核）。

```
[資料層] 開放資料湖（進出站、車站、時刻、通阻）
[特徵層] 每日批次特徵表
[模型層] Baseline + 進階模型；模型卡（訓練日、指標、限制）
[服務層] 預測 API／批次結果表
[應用層] 可解釋儀表板（Streamlit 或同等）
[治理層] 資料來源表、AI 使用紀錄、人工覆核日誌
```

**圖 4　儀表板資訊架構**

1. **總覽 KPI**：全線／選定路線今日預估負荷、較平日變化％、預警站數  
2. **車站檢視**：歷史＋預測曲線、信賴／誤差帶（或以近期 MAPE 示意）  
3. **解釋區**：Top 特徵；最相似之歷史日（距離度量於特徵空間）  
4. **建議區**：依規則輸出文字建議（例：連假前一日、預估高於常態 30% → 建議加強站內動線與旅客即時資訊）  
5. **資料與模型透明度**：資料更新日期、模型版本、已知限制  

**決策使用者**：場站管理／疏運規劃（主）；旅客資訊服務企劃（次）；後續可延伸旅遊行程提示（旅途探索家）。

### 六、可解釋性與人機協作機制

1. **全域解釋**：特徵重要性排序（依車站分群比較）。  
2. **在地解釋**：單一預測日之主要貢獻特徵條列。  
3. **案例解釋**：檢索「特徵相近的歷史日」及其實際運量與當時情境（是否連假／通阻）。  
4. **人工覆核**：所有建議預設「建議—確認—執行」；系統不自動下指令。  
5. **失敗模式揭露**：資料延遲、極端天候、突發大型活動未標記時之風險。

此設計對齊「資料驅動決策支援」敘事：預測是手段，**可被採納的決策語言**才是產品。

### 七、評估指標與驗證計畫

**表 4　評估指標**

| 類型 | 指標 | 用途 |
|------|------|------|
| 預測精度 | MAE、MAPE、RMSE（分站／分群） | 模型選型 |
| 基準增益 | 相對 baseline 之誤差下降％ | 證明複雜度合理 |
| 預警品質 | 偏離事件之 Precision／Recall（以歷史極端日定義） | 決策相關性 |
| 決策效用（原型） | 假設任務：給定預測＋解釋，受測者完成「是否加強整備」判斷之時間與一致性 | DSS 價值 |
| 系統可用性 | 任務完成率、錯誤點擊（小規模易用性） | 決選 Demo |

驗證原則：嚴格時間切分；連假與平日分層報告；禁止以隨機切分造成洩漏。

### 八、預期成果、落地情境與風險

#### （一）海選交付（本企劃）

- 完整研究設計、資料來源與方法論  
- 系統與儀表板資訊架構  
- 評估與期程、風險對策  

#### （二）決選可展示成果（規劃）

- 可操作 Demo：選站 → 未來 7 日預測 → 解釋 → 建議文案  
- 1–2 個連假或觀光站案例故事板  
- 與 baseline 對照之量化結果海報／簡報頁  

#### （三）落地情境舉例

1. **連假疏運整備**：H-7 至 H-1 預估熱點站清單與變化幅度。  
2. **觀光支線營運**：周末／活動日進出站預估，支援接駁與站內資訊。  
3. **通阻後恢復監測**：事件後運量是否偏離模型預期，輔助服務恢復溝通。  

#### （四）風險與對策

| 風險 | 對策 |
|------|------|
| 公開資料更新延遲 | 儀表板標示資料新鮮度；預測標註信心降級 |
| 結構斷點（票務改版／疫情） | 分時期模型、虛擬變數、敏感度分析 |
| 無細粒度 OD | 本期以站日負荷為主；晉級後申請內部資料再擴充 |
| AI 過度依賴疑慮 | 核心架構與評估由團隊定義；AI 僅輔助文獻整理與文案潤飾並據實填報 |
